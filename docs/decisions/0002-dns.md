# 0002: Use the system resolver, timed inside the lookup thread

## Decision

misura resolves names with the system resolver (`getaddrinfo`, through `ToSocketAddrs`), the same one other programs on the machine use.
The lookup runs on a blocking thread so a timeout can apply, and the DNS time is measured inside that thread, around the `getaddrinfo` call alone.

A future `--resolver IP` option would query that server directly with `hickory-resolver`.

## Why the system resolver

The question misura answers is "why is this request slow for me?", so it has to resolve names the way the user's other programs do.
On macOS that matters a lot: `getaddrinfo` follows scoped resolvers in `/etc/resolver/`, VPN and Tailscale split DNS, and mDNS for `.local` names.
`hickory-resolver` reads `/etc/resolv.conf` and would miss all of those, reporting different addresses or timings than the user actually gets.
For asking one specific server, hickory stays useful.

## Why time inside the thread

`tokio::net::lookup_host` runs `getaddrinfo` on tokio's blocking pool.
Measured around the call, it adds about 0.1–0.15 ms of thread hand-off that isn't DNS:

| Lookup of `localhost` | Run 1 | Run 2 | Run 3 |
| --- | --- | --- | --- |
| `getaddrinfo` on the calling thread | 136 µs | 18 µs | 11 µs |
| `tokio::net::lookup_host`, timed around the call | 288 µs | 166 µs | 111 µs |

Calling `getaddrinfo` directly on the main thread would be accurate but couldn't be cancelled, and a stuck resolver can block for several seconds.
Running it on a thread and timing inside that thread keeps both the accuracy and `--timeout`.

## Not yet decided

When a name resolves to several addresses, the spike tries them in order and records which one connected.
Happy Eyeballs (RFC 8305: racing IPv6 against IPv4) is what browsers and curl do.
This container resolves `localhost` to IPv4 only, so it couldn't be tested here; check it on a dual-stack machine.
